## 1. Conventions

| Topic | Rule |
| --- | --- |
| Versioning | Path version `/api/v1`. Breaking changes require `/api/v2`; additive fields are allowed within v1 |
| Resource names | plural, `kebab-free` (`/exchange-rates`, not `/exchangeRates`) |
| JSON fields | `snake_case` |
| Identifiers | UUID v4 strings |
| **Money** | **decimal string** (`"70000.0000000000"`), never a JSON number — JSON numbers are IEEE-754 in most runtimes (PART 62) |
| Quantities (currency units) | decimal string |
| Rates | decimal string with up to 10 dp |
| Timestamps | ISO-8601 UTC with `Z` (`2026-09-11T08:14:03.117Z`). Display timezone is a client concern |
| Dates (filters, business dates) | `YYYY-MM-DD` interpreted in the branch's timezone when `branch_id` is given, otherwise UTC |
| Request id | `X-Request-Id` accepted and echoed; generated if absent; appears in logs and audit rows |
| Pagination | `limit` (default 50, max 200), `offset`; responses carry `total`. The sync feed uses a cursor instead |
| Sorting | `sort=field` / `sort=-field`; whitelisted per endpoint |
| Content | Requests with unknown fields are rejected (`422`) — typos must not be silently ignored on money endpoints |
| Compression | gzip/br for responses > 1 KB |
| CORS | Explicit allowlist from `CORS_ORIGINS`; credentials only for the web admin origin |
| Health | `GET /api/v1/health` (liveness), `/health/ready` (DB+Redis), `/version` (build SHA) |

## 2. Authentication

OAuth2-compatible password flow with JWT access tokens and rotating refresh tokens bound to a registered device.

| Method | Path | Auth | Permission | Purpose |
| --- | --- | --- | --- | --- |
| `POST` | `/auth/login` | public | — | Username/password → access + refresh + device binding |
| `POST` | `/auth/refresh` | refresh token | — | Rotate the refresh token, issue a new access token |
| `POST` | `/auth/logout` | access token | — | Revoke the current refresh family (and optionally all devices) |
| `GET` | `/auth/me` | access token | — | Identity, roles, effective permissions, device, branch |
| `GET` | `/auth/sessions` | access token | — | Active refresh-token families for the calling user (own devices only) |
| `POST` | `/auth/sessions/{session_id}/revoke` | access token | — | Revoke one of the caller's own sessions (audit `SECURITY_SESSION_REVOKED`) |
| `POST` | `/auth/password` | access token | — | Change own password (revokes every other session) |
| `GET` | `/auth/ping` | access token | — | Cheap token/device validity probe used before a shift |

```json
  "refresh_expires_in": 2592000,

  "user": {"id": "33333333-…", "username": "cashier1", "full_name": "Cashier One",
```

Semantics and security:

| Rule | Detail |
| --- | --- |
| Access token | JWT, HS256/RS256 per config, `exp` = `ACCESS_TOKEN_EXPIRE_MINUTES` (default 15), claims: `sub`, `jti`, `did` (device), `bid` (branch), `roles`, `perm_hash`, `iat` |
| Refresh token | Opaque 256-bit random value; only its SHA-256 is stored (`refresh_tokens.token_hash`) |
| Rotation | Every refresh issues a new token in the same `family_id`; the used token is marked `used_at` |
| Reuse detection | Presenting a used token revokes the whole family, writes a `SECURITY_REFRESH_REUSE_DETECTED` audit event and returns `401 TOKEN_REVOKED` |
| Device binding | Token carries the device; a token used from another device id is rejected (`401 DEVICE_MISMATCH`) |
| Unknown device | Rejected unless the caller holds `device.register` or the branch's device auto-registration policy applies |
| Revoked device | `401 DEVICE_REVOKED` on every request, including sync |
| Lockout | After `N` failed logins (default 5) within the window, `locked_until` is set; `423 ACCOUNT_LOCKED` |
| Failed logins | Recorded in `users.failed_login_attempts` and emitted as `AUTH_LOGIN_FAILED` audit events |
| Password change | `POST /auth/password` verifies the current password, enforces the policy (12–128 chars, not common, ≠ username/full name), clears `must_change_password` and revokes every refresh family of the user except the calling one |
| Password policy rejection | `422 VALIDATION_ERROR` with `details.fields = [{"field": "new_password", "code": "policy"}]` |
| Forced change | A user with `must_change_password = TRUE` authenticates but every permission-guarded endpoint answers `403 PERMISSION_DENIED` with `details.reason = PASSWORD_CHANGE_REQUIRED` and `details.allowed_endpoints = [/api/v1/auth/password, /api/v1/auth/logout, /api/v1/auth/me]` |

### 2.2 Authorization and session lifecycle (implemented in Phase 2)

| Rule | Detail |
| --- | --- |
| Deny by default | Every protected route is wrapped in a FastAPI dependency (`require_permission` / `require_any_permission`); a route that forgets one is answered `401`, never open |
| Effective permissions | `role_permissions` grants minus any `user_permissions` row with `is_granted = FALSE`; an explicit deny always wins |
| Per-request re-read | User, roles, permissions and device are re-read from PostgreSQL on every request (no cached authority in the token) |
| Authority fingerprint | The access token carries `perm_hash`; if the stored authority changed, the request is rejected `401 TOKEN_INVALID` with `details.reason = AUTHORIZATION_CHANGED` so the client refreshes instead of acting on a stale permission set |
| Account/session gone | Deactivated user or revoked device/session inside a still-valid token → `401 TOKEN_INVALID` with `details.reason = SESSION_GONE` / `DEVICE_REVOKED` |
| Escalation guards | An administrator cannot grant what they do not hold: assigning a system role they lack → 403 `PERMISSION_DENIED` `details.reason = SYSTEM_ROLE_ESCALATION`; assigning a role or grant that would confer an unheld permission → 403 with `details.reason = PERMISSION_ESCALATION` (`details.missing_permissions`, `details.attempted_roles`). Refusals are audited (`SECURITY_PRIVILEGE_ESCALATION_BLOCKED`) |
| Self-edit guards | A user cannot deactivate or lock out themselves (`details.reason = self_deactivation` / `self_lockout`) or delete the last active `SUPER_ADMIN` |
| Session revocation | Logout revokes the current refresh family; `all_devices` revokes every family of the user (`revoked_sessions` in the response); password change and device revocation kill sessions immediately |
| Access-token revocation | `jti` values of revoked access tokens live in a Redis denylist for their remaining lifetime; if Redis is unavailable, revocation checks **fail closed** with `503 SERVICE_UNAVAILABLE` |

## 3. Error envelope (PART 38)

Every non-2xx response:

```json
{
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "Insufficient AFN balance for this payout.",
    "details": {
      "branch_id": "11111111-…",
      "currency_code": "AFN",
      "available": "69500.0000000000",
      "required": "70000.0000000000"
    }
  },
  "request_id": "0f8b0f2e-…"
}
```

* `code` — stable, machine-readable, `SCREAMING_SNAKE_CASE`.
* `message` — human-readable, safe to display, **localisable by code on the client** (the server message is a fallback).
* `details` — structured context; never contains secrets, hashes or tokens.
* Validation errors (`422`) add `details.fields`: `[{"field": "from_amount", "code": "greater_than", "message": "must be > 0"}]`.

## 6. Idempotency (PART 40)

Required (`Idempotency-Key: <uuid>`) for `POST /exchange`, `POST /exchange/{id}/cancel`, `POST /exchange/{id}/reverse`, `POST /transfers`, `POST /transfers/{id}/approve|pay|cancel`, `POST /cash/in`, `POST /cash/out`, `POST /cash/close`, `POST /expenses`.

| Case | Behaviour |
| --- | --- |
| First use | Row created `IN_PROGRESS` in the same transaction as the effect; response stored (`COMPLETED`) |
| Repeat, same body | Stored response replayed with the original status code and an `Idempotency-Replayed: true` header |
| Repeat, different body | `409 IDEMPOTENCY_KEY_REUSED` |
| Concurrent duplicate | `409 IDEMPOTENCY_IN_PROGRESS` (`Retry-After: 1`) |
| Missing key on a required endpoint | `400 IDEMPOTENCY_KEY_REQUIRED` |
| Retention | 30 days, then pruned by the worker |

## 7. Rate limits (PART 42)

| Scope | Default | Response |
| --- | --- | --- |
| `POST /auth/login` | 10 / 5 min / (IP, username) | `429 RATE_LIMITED` + `Retry-After` |
| `POST /auth/refresh` | 60 / min / device | same |
| Financial writes | 120 / min / user | same |
| Reads | 600 / min / user | same |
| `POST /sync/push` | 30 / min / device, batch ≤ 50 events | `429` + `Retry-After`; client halves the batch |
| Edge (nginx) | 20 r/s per IP burst 40 | `429` before the app |

Implementation notes: every throttled response carries `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Window` and `Retry-After`; the login bucket is keyed by `login:{IP}:{username}` and is **not** cleared by a successful login (a mixed success/failure pattern cannot reset the counter); the refresh bucket is keyed by `refresh:{device_uuid}`; a throttled request is rejected inside the limiter dependency, before any service call, so it writes no audit row and does not touch `failed_login_attempts`; if Redis is unavailable the limiter fails closed (`503 SERVICE_UNAVAILABLE`) when `RATE_LIMIT_FAIL_CLOSED=true` and fails open otherwise (the database lockout still applies).

```json
  "receipt": {"url": "/api/v1/exchange/bbbbbbbb-…/receipt"}
}
```

Server-side rules: `to_amount` is **computed** (`from_amount × rate − commission` for `BUY`) and must match the client's value within one minor unit, otherwise `422 AMOUNT_MISMATCH` — the client never dictates a computed total (PART 63).

Errors specific to this endpoint: `RATE_NOT_FOUND`, `RATE_OUT_OF_TOLERANCE`, `INSUFFICIENT_BALANCE`, `CURRENCY_INACTIVE`, `CUSTOMER_INACTIVE`, `FORBIDDEN_SCOPE`, `CASH_SESSION_NOT_OPEN`.

### 9.6 Reports

All report endpoints accept `from`, `to` (ISO dates, branch-local when `branch_id` is given), `branch_id`, `currency_id`, `cashier_id`, and return `Content-Type: application/json`; `?format=csv|xlsx|pdf` (where supported) requires `reports.export`.

| Path | Returns |
| --- | --- |
| `GET /reports/daily` | Per-day, per-branch, per-currency: counts, volumes, commissions, FX result, net cash movement |
| `GET /reports/profit-loss` | Revenue − expenses from the ledger, by account and period, with prior-period comparison |
| `GET /reports/cash` | Opening, movements by type, closing, expected vs counted, differences |
| `GET /reports/exchange` | Transactions grouped by pair/type/cashier with rates and margins |
| `GET /reports/customers` | Volume per customer, last activity, outstanding balances |
| `GET /reports/transfers` | Lifecycle funnel (created/approved/paid/cancelled), fees, ageing |
| `GET /reports/trial-balance` | `v_trial_balance` per account/currency with Σdebit = Σcredit assertion |
| `GET /reports/general-ledger` | Journal lines per account with running balance and document links |

Every report response carries `"source": "journal_lines" | "cash_movements" | "exchange_transactions"` so a reader always knows which immutable table produced it, plus `"generated_at"` and `"filters"`.
